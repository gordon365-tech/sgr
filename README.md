# SGR

SGR is an AI powered multi asset trading system designed around a modular, risk first architecture. The platform provides market data ingestion, feature engineering, strategy execution, portfolio management, risk controls, exchange connectivity, persistence, monitoring and a FastAPI based service layer.

> **Current trading mode:** Paper trading is the default. Live trading must only be enabled after the required operational and risk controls have been validated.

## Architecture

The system is organized as a processing pipeline:

```text
Market Data
    ↓
Feature Store / Feature Engineering
    ↓
Strategy Engine
    ↓
Signal
    ↓
Risk Engine
    ↓
Position Sizer / Kill Switch
    ↓
Portfolio
    ↓
Order Execution
    ↓
Exchange Adapter
```

Core components include:

| Component | Responsibility |
|---|---|
| `market_data` | Market data ingestion, normalization, gap detection and feature storage |
| `strategy` | Strategy registration, selection and signal generation |
| `risk` | Portfolio risk, VaR, position sizing and kill switch controls |
| `portfolio` | Positions, PnL and portfolio state |
| `execution` / exchange layer | Exchange abstraction and order execution |
| `backtesting` | Historical simulation and performance evaluation |
| `ml` | Regime detection, volatility forecasting and related ML capabilities |
| `sentiment` | News and sentiment processing |
| `api` | REST and WebSocket interfaces |
| `core` | Configuration, persistence, logging, encryption and event infrastructure |
| `monitoring` | Prometheus and Grafana integration |

The repository is intended to keep strategy logic, risk controls and exchange connectivity separated so that individual components can be tested and evolved independently.

## Configuration

Create a local environment file from the example:

```powershell
Copy-Item .env.example .env
```

Never commit `.env` or real exchange credentials to source control.

The configuration separates paper and live exchange credentials. Keep the system in paper mode while developing and testing:

```text
TRADING_MODE=paper
```

Important configuration areas include database connectivity, Redis, API security, encryption, risk limits, exchange credentials and monitoring.

## Docker Development Environment

The development stack provides the API, PostgreSQL / TimescaleDB, Redis, Prometheus and Grafana.

From the repository root:

```powershell
docker compose -f docker/docker-compose.yml up -d --build
```

Check the running services:

```powershell
docker compose -f docker/docker-compose.yml ps
```

Follow API logs:

```powershell
docker compose -f docker/docker-compose.yml logs -f api
```

Stop the environment:

```powershell
docker compose -f docker/docker-compose.yml down
```

To remove the development database and Redis volumes as well:

```powershell
docker compose -f docker/docker-compose.yml down -v
```

The default development endpoints are:

| Service | Endpoint |
|---|---|
| SGR API | `http://localhost:8000` |
| FastAPI Swagger UI | `http://localhost:8000/docs` |
| FastAPI ReDoc | `http://localhost:8000/redoc` |
| Prometheus | `http://localhost:9090` |
| Grafana | `http://localhost:3001` |
| PostgreSQL | `localhost:5433` |
| Redis | `localhost:6379` |

## Running the API without Docker

Install the project and development dependencies in a virtual environment:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -e ".[dev]"
```

Start the API with:

```powershell
uvicorn sgr.api.main:app --host 0.0.0.0 --port 8000 --reload
```

The exact import path assumes the repository is checked out with the package directory structure intact.

## Database Migrations

Alembic is used for database schema management.

Apply migrations with:


```powershell
alembic revision --autogenerate -m "describe change"
```

Review autogenerated migrations before applying them to any persistent environment.

## Testing

The project uses Pytest. The configured test suite includes unit and integration style tests covering configuration, encryption, exchanges, market data, ML components, risk, strategies, portfolio behaviour, repositories, API behaviour and SaaS functionality.

Run the complete configured suite:

```powershell
pytest
```

For a functional run without the coverage gate:

```powershell
pytest --no-cov
```

Inside Docker:

```powershell
docker compose -f docker/docker-compose.yml exec api python -m pytest --no-cov
```

Collect tests without executing them:

```powershell
docker compose -f docker/docker-compose.yml exec api python -m pytest --collect-only -q
```

The repository currently configures an 85 percent coverage threshold. A failing coverage gate does not by itself prove that functional tests are failing, so functional test results and coverage results should be evaluated separately.

## Risk Controls

Risk management is a first class subsystem rather than an optional strategy feature. The configuration contains explicit limits for:

* Maximum portfolio drawdown
* Daily loss
* Maximum single position exposure
* Value at Risk
* Portfolio heat
* Maximum leverage
* Maximum number of open positions

The kill switch is intended to stop or pause trading when defined risk conditions are breached.

Do not treat these defaults as production approved risk parameters. They are development configuration and must be reviewed, validated and approved for the intended deployment.

## Exchange Connectivity

The exchange layer is abstracted behind exchange adapters. The current codebase contains adapters and clients for exchanges including Pionex and Binance, with CCXT based infrastructure available for supported exchanges.

Pionex uses the symbol convention:

```text
BTC_USDT
```

The Pionex public market client can operate without private trading credentials for public market data. Paper trading is the preferred mode for development.

Live credentials must never be stored in the repository, Docker images or source code.

## API

The FastAPI application exposes health, market, portfolio, risk, strategy, order and system functionality together with WebSocket streams.

The intended API surface includes:

```text
/health
/api/v1/market
/api/v1/portfolio
/api/v1/risk
/api/v1/strategy
/api/v1/orders
/api/v1/system
/ws
```

Interactive API documentation is available at `/docs` in non production environments.

## Observability

Prometheus is used for metrics collection and Grafana provides dashboards. Structured logging and optional OpenTelemetry tracing are supported through the monitoring configuration.

The health endpoint is designed to provide a quick indication of the state of critical components such as the exchange pool, feature store, risk engine and market data layer.

## Security

Security sensitive configuration includes:

* API secret keys
* Encryption master key
* Exchange API credentials
* Database passwords
* Optional Telegram and Sentry credentials

Use strong production secrets and keep them outside source control. The example values in `.env.example` are development placeholders only.

Before enabling live trading, validate authentication, authorization, secret handling, network controls, risk limits, kill switch behaviour, exchange permissions, logging and monitoring independently.

```text
Run focused tests
   ↓
Run functional suite
   ↓
Run lint / type checks
   ↓
Run Docker validation
```

For trading related changes, functional correctness and risk behaviour should be validated before coverage optimization.

## Project Status

SGR is an active development project. The architecture already contains the principal building blocks for a complete trading pipeline, but the system should not be considered production ready solely because the API or Docker stack starts successfully.

Production readiness requires, at minimum, a fully reproducible green functional test baseline, validated risk controls, deterministic paper trading behaviour, exchange specific validation, secure secret management, observability, failure recovery testing and an explicit live trading approval process.
