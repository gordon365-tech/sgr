ARCHITECTURE IMPLEMENTED
=========================

Event-Driven Trading Cycle
---------------------------

  1. CANDLE EVENT
     Redis Event Bus publishes CandleEvent (OHLCV data + indicators)
     ↓
  2. STRATEGY SIGNAL
     StrategyEngine.process() generates Signal with confidence
     → Publishes SignalEvent on Event Bus
     ↓
  3. RISK ASSESSMENT
     RiskEngine.evaluate() analyzes portfolio risk metrics
     → Calculates position size based on risk limits
     → Publishes RiskApprovedEvent or RiskRejectedEvent
     ↓
  4. EXECUTION
     ExecutionEngine.execute() sends OrderRequest to exchange adapter
     → Paper adapter: simulates immediate fill
     → Live adapter: submits to Pionex, monitors for fills
     → Publishes OrderFilledEvent on Event Bus
     ↓
  5. PORTFOLIO UPDATE
     PortfolioEngine.on_order_filled() updates:
     → Opens new position or reduces existing position
     → Updates cash available
     → Calculates unrealized PnL
     → Records position in database (for recovery)
     ↓
  6. MONITORING & AUDIT
     - All events published on Redis Event Bus
     - All events logged with structured logging (JSON)
     - All orders persisted to PostgreSQL
     - All positions recoverable after crash

Hybrid Synchronous/Event-Driven Design
---------------------------------------

Control Flow: Direct awaited method calls (StrategyEngine → Risk → Execution → Portfolio)
  - Ensures deterministic order of operations
  - No race conditions or parallel branches
  - Synchronously testable without Redis

Event Bus: Used additively for observability/audit
  - RiskApprovedEvent, RiskRejectedEvent, OrderFilledEvent published
  - Can be monitored in real-time
  - Decouples monitoring from trading logic
  - Fail-safe: bus errors never block trading execution

Key Design Pattern: "Fail-Safe"
  - Each Event Bus publish wrapped in try/except
  - Every unexpected exception in trading cycle → logged, not thrown
  - Database errors → logged, not blocking portfolio updates
  - Network timeouts → retried with exponential backoff
  - Result: Trading always completes; observability is best-effort

Crash Recovery Flow
-------------------

On Application Startup:
  1. Repositories initialized (PositionRepository, OrderRepository)
  2. RecoveryManager.recover_after_crash() called:
     - Loads open positions from database
     - Restores portfolio state
     - Validates exchange state matches local state
  3. Market Data Engine subscribes to CandleEvents
  4. Orchestrator subscribes to on_candle_event()
  5. Trading resumes automatically


SAFETY FEATURES VERIFIED
==========================

1. Kill Switch Protection
   - Configured as default per-symbol and global
   - Hard limit breach (>15% drawdown) triggers automatically
   - Prevents order submission when active
   - Can be manually triggered via /api/v1/system/kill-switch
   - Reset via same endpoint with admin token

2. Risk Rejection Path
   - RiskEngine.evaluate() returns REJECTED when:
     * Portfolio drawdown exceeds hard limit
     * Daily loss exceeds hard limit
     * Leverage exceeds max allowed
     * Position correlation too high
   - REJECTED signals → No order sent → Position not opened
   - Event: RiskRejectedEvent published with reason

3. Soft Limit Handling
   - VaR limit breach → Position size reduced to 50%
   - Portfolio heat limit → Position size reduced to 25%
   - Correlation exposure → Position reduced proportionally
   - Result: RiskDecision.REDUCED with approved_quantity < requested

4. Paper Trading Default
   - Default configuration: TradingMode.PAPER
   - No exchange API keys required
   - Paper adapter simulates all fills at market price
   - Production usage: set TRADING_MODE=paper in environment
   - LIVE mode: requires explicit environment config + API keys

5. Position Sizing
   - Risk Engine applies multiple constraints:
     * Max single position: 5% of portfolio (configurable)
     * Max portfolio heat: 70% (configurable)
     * Max portfolio leverage: 3x (configurable)
     * Max order notional: $50,000 (configurable)
   - Result: No single trade can exceed risk bounds
   - Verified: Position never > approved quantity

6. Cooldown Mechanism
   - Prevents overtrading on same symbol+strategy
   - Default: 60 seconds between trades (configurable)
   - Configurable: trade_cooldown_seconds in risk_limits
   - Bypass: set trade_cooldown_seconds=0 (not recommended)
